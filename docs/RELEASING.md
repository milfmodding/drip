# Building a release

What a player downloads, who assembles it, and what has to be true first.

For the player-facing side — install steps, options, troubleshooting — see the `README.txt`
that ships inside each archive. Both are generated by `tools/build-release.py`, so edit them
there rather than by hand.

---

## What a player gets

**Two kinds of archive.** Part 1 ships inside the mod as the minimal working install; Parts 2
and 3 are separate downloads.

`DRIP-<version>.zip` — the base install:

```
DRIP/
  DRIP.dll  + its dependencies        the built mod
  config/config.jsonc                 the options they can change
  bundles/ContentPacks/Essentials/    item configs and their .bundle files, side by side
  README.txt
```

`DRIP-<pack>-<version>.zip` — one add-on pack, content only:

```
DRIP/
  bundles/ContentPacks/<Pack>/        configs, bundles, and pack-info.json
  README-<Pack>.txt
```

Both extract into `<SPT>\user\mods\`. An add-on merges into the install and adds one folder;
it carries no assembly, no config, and no other pack's files, so it cannot overwrite anything
the base install provided. `verify_stage` enforces that rather than trusting the path walk —
an add-on that picked up a base file is refused, not shipped.

The end state is `<SPT>\user\mods\DRIP\DRIP.dll`. The most common install mistake is one folder
too deep — `...\mods\DRIP\DRIP\DRIP.dll` — so the README calls that out specifically.

**Version skew.** Each add-on carries `pack-info.json` stamped with the DRIP version it was
built from, and its README says what to check if that differs. A pack is only configs and
bundles, so a mismatch is usually harmless — the stamp exists to make it *diagnosable*, not to
refuse the install.

**Updating.** Re-extract the base archive over the top; add-on packs are untouched. Removing a
pack means deleting its folder. There is deliberately no in-place update path — once bundles
are hollowed out, re-extracting is cheap enough not to need one.

## Why `ContentPacks/` is the mechanism

A content pack is a self-describing directory: the loader enumerates whatever it finds. That is
what makes an add-on "just a folder appearing", and it is also the route a third party would use
to ship DRIP content inside a larger mod of their own. When that lands, it must resolve to the
same code path as ours — nothing here should grow an assumption that a pack came from a DRIP
archive.

---

## Why this needs a script

The repository holds the configs; the bundles are deliberately kept out of git and live in
`F:\SPT\Mods\DRIP-bundles\`. A release therefore has to be assembled from two places, which is
why `git archive` or zipping the source folder won't do it. Either produces an archive that
installs cleanly and then loads nothing.

## Building one

```bash
python tools/build-release.py              # the base install (mod + Essentials)
python tools/build-release.py --all        # base plus every add-on pack present
python tools/build-release.py --pack Part2 # one add-on on its own
```

It refuses to package anything it hasn't verified. In order:

1. **`drip check`** over the content — any error stops the build.
2. **Release readiness** — every item's required bundles are present in the store.
3. **`dotnet build -c Release`**.
4. **Stage** the build output, then overlay bundles from the store.
5. **Verify the staged tree** — every item has its bundles *in the package*; a base archive has
   the assembly, the config folder and only the base pack; an add-on has none of those.
6. **Write the README**, then compress into `dist/`.

Steps 2 and 5 check the same property at different moments on purpose. Step 2 fails in a second
and tells you a release isn't possible; step 5 catches anything that went wrong during the copy
itself. The failure being guarded against is a release that looks fine and ships an item with no
model.

Useful flags:

| flag | for |
|---|---|
| `--check-only` | *"could we ship right now?"* — copies nothing, answers **per pack**, in about a second |
| `--all` | base plus every add-on pack present |
| `--pack <name>` | one add-on pack on its own |
| `--skip-build` | package an existing Release build |
| `--no-zip` | leave the staged folders for inspection |
| `--store-only` | produce only the bundle-store assets Setup.cmd downloads |
| `--no-store-zip` | skip the store assets a full build normally also produces |

`--check-only` reports each pack separately, because an add-on can be unshippable while the
base install is fine — and in that case the base should still ship.

The version comes from `<Version>` in `DRIP.csproj`, so bump it there.

## The bundle-store assets (developer bootstrap)

Every build also produces — or `--store-only` produces alone — the assets a fresh clone's
`Setup.cmd` downloads so a new developer needs nothing but clone + double-click:

```
dist/DRIP-bundle-store-01.zip, -02.zip, ...     the store's bundles, split under GitHub's 2 GiB cap
dist/DRIP-bundle-store.json                     manifest: part names, file and byte counts
```

**The three names are stable across releases on purpose.** Setup.cmd fetches
`<repo>/releases/latest/download/DRIP-bundle-store.json` and then the parts the manifest
names, so a new developer never has to know the version. Upload them to the same GitHub
release as the player archives — they are not player installs and the README in them says so.

Each part is a complete zip of a subset of files (not a byte-split join), so extracting is
just "unzip every part into the store folder"; Setup.cmd verifies each part's CRC before
extracting it and stops naming the part if one is corrupt. Bundles only — configs come from
git, and shipping them twice would be one more place for the two to disagree.

The store the assets are cut from is the same one releases are assembled from, so the
checklist's "regenerate the store after any change to PROMOTIONS/RENAMES" applies to these
uploads too.

## Two gates that come before everything below

**Sophia's, 2026-07-30, and she asked to be held to them even when it is inconvenient.** These
are not checklist items to tick on the day — they are work, and they need scheduling like work.

### Gate 1 — every word a human reads is written by a human

> *"Don't let me generate prose. Everything like READMEs, the mod description on the forge, any
> public-facing docs, all has to be written by me. You folks are welcome to review what I've
> written and suggest updates."*

The reasoning is hers and it is not about quality: **she is not willing to hand SPT's moderators
another AI-generated mod.** That is a judgement about what it means to put your name on
something, and it is not ours to optimise around.

**The surface is larger than "READMEs", and this is the part most likely to be missed.** If a
human will read it, it counts. Enumerated honestly, because discovering this late is how the gate
gets skipped:

| Surface | Written by | Read by |
|---|---|---|
| Forge description, README, changelog | not yet written | players, moderators |
| `AUTHORING.md`, `CONFIG-SCHEMA-v2.md`, `VALIDATION.md` | Tau | Colette, Amber |
| `REPRICE-WORKSHEET.md`, `CLIENT-SMOKE-TEST.md` | Echo | Sophia, Colette, Amber |
| **Every comment in every shipped `.jsonc`** | Tau / converter | Colette and Amber, daily |
| **`drip check` diagnostics, `Setup.cmd` output, `drip new` scaffolding** | Tau | Colette and Amber, daily |
| Item names and descriptions in `CustomLocales/` | authored in 3.x | **every player, in game** |

The last three rows are the ones that matter most and read least like "documentation". A player
never opens `AUTHORING.md`; they read item descriptions. Colette never reads the forge post; she
reads config comments every time she opens a file.

**Internal coordination is explicitly exempt** — `STATUS.md`, the pre-registrations,
`tools/bundles/README.md`, cross-agent messages. Nobody outside the team reads those.

### Gate 2 — Sophia reviews the code and can demonstrate she can maintain it

> *"Before we push to the forge, I MUST review the code myself, and demonstrate that I understand
> what it does and how to update it on my own."*

Not a skim. The test she set is **being able to change it without us**, which is the right test:
this mod outlives any session, and a maintainer who cannot modify their own mod is dependent on
whoever wrote it.

Scope: **~4,300 lines of C# across 19 files**, plus `tools/drip.py` and
`tools/convert-legacy.py`. That is a real time commitment and it should be booked, not squeezed
in on release day.

**Reading order (Kappa's, and his reasoning is better than the first draft's):**

1. **`Models/ContentItemConfig.cs`** — first, because it is the only file that maps onto something
   Sophia already knows. She has read hundreds of configs; this is their vocabulary. Starting at
   `DRIP.cs` would start with load order, which is the most surprising thing in the codebase and
   the least connected to anything she has seen.
2. **`DRIP.cs`** — but for the **sequence in `OnLoad`**, not the priority. That method is the whole
   mod in thirty lines: traders, locales, quests, items, clothing, cross-pack fixups, self-check.
   Read it and you know what exists. The load-order comment is now longer than the code it
   annotates; read once, then leave alone.
3. `Services/DRIPCustomItemService.cs` and `DRIPCustomClothingService.cs` — the bulk.
4. `Services/DRIPTraderAssortService.cs` — the subtlest, and the one whose behaviour surprised
   both Echo and Kappa.
5. `Services/DRIPVerificationService.cs` — **last, but read it properly.** Every assertion names a
   real bug, so it doubles as the list of ways this mod has actually broken. It is the cheapest
   history of the codebase there is.

**If time gets squeezed, the honest priority** (Kappa's, and it is not proportional to line
count): she can confidently change **configs, the self-check and the assort service**, and *knows
not to touch* the five below. The two big services are ~2,100 of the 4,300 lines and carry most of
the real complexity — understanding `DRIPCustomClothingService` end-to-end is a much bigger ask
than its length suggests. `Utils/` is 244 lines and readable in a sitting.

### The five that must be told, because they cannot be discovered

Each is locally sensible code whose constraint **lives outside the file**. These are what fail
silently after an edit, when nobody is around to notice.

1. **The `+ 2` in DRIP's load priority.** It means "one slot after WTT-ServerCommonLib". Nothing in
   the code expresses it, DRIP declares no dependency on WTT, and every signal available to a
   tidy-up says renumber it to `+ 0`.
2. **Renaming a config file changes its item id permanently — and breaks saves.** The id derives
   from the filename via `DripIds`. Rename `SLICK_CADPAT_ARMOR.jsonc` and anyone who owns the old
   item now owns one whose template does not exist, which is exactly the profile invalidation
   fixed on 2026-07-29. **Free before release, save-breaking after**, and nothing says so at the
   point of danger. Kappa rates this the worst of the four, because the damage is to a player's
   save rather than to the mod.
3. **`DripJson.Options` vs `SptTypeOptions` differ by one flag and it is load-bearing.** DRIP's own
   configs bind case-insensitively; SPT model types must not, because `TemplateItemProperties`
   declares both `ShotgunDispersion` and `shotgunDispersion` and case-insensitive binding makes the
   type unconstructable. Using the wrong one breaks thirty armour items and nothing else. The
   reason is a BSG type's duplicate property names — **invisible from DRIP's side entirely.**
4. **Fence's assort is generated at `TraderCallbacks` (800,000), not loaded at `DatabaseImporter`.**
   Fence's `assort.json` on disk is empty, which reads as "no data" rather than "filled in later".
   This is why DRIP cannot mirror Fence at its current priority, and why 13 items need their own
   prices.
5. **Quest-locked offers are deliberately not copied.** The code declines them and declining looks
   like a bug until you know the 3.x leak at `collection.ts:213-217`. **This is the one most likely
   to be "fixed" by a well-meaning maintainer** — see the seven items in `REPRICE-WORKSHEET.md`.

The companion list from Kappa's dead-code pass is **`LOOKS-REMOVABLE.md`**: what looks removable and
is not. A new maintainer can find what is used; what they cannot find is what appears unused and is
load-bearing — nine `AbstractModMetadata` overrides with no reference anywhere would look like the
safest nine deletions available, and removing them stops the mod loading. It also records the four
categories that produce false positives, and the measurement that a naive sweep flags 99 of 181
declared names with roughly zero true positives.

**Our job here is to answer questions, not to narrate.** If she asks "what does this do", the
useful answer is the one that leaves her able to answer it herself next time.

### Sequencing: the two gates must not be worked in the same pass

**Tau's, and it belongs to neither gate individually, which is why it is here.**

Gate 1 has Sophia rewriting all 32 `drip check` diagnostics. The planned registry refactor (see
`CHECK-REGISTRY-DESIGN.md`) has one safety property: it is **behaviour-preserving, verified by
`drip check` producing byte-identical output over the live pack before and after.**

**That verification evaporates the moment the strings change.** Do both at once and neither diff
is reviewable — which is exactly how a refactor that "obviously changed nothing" ships a silently
dropped check.

**Wording first or structure first. Either order works; both at once does not.**

The same rule applies to any other pairing of a prose pass with a mechanical one — the config
comment templates and the converter, for instance.

## Before a real release

- [ ] **Gate 1: all human-read prose written by Sophia** (see above — including config comments,
      tool output and in-game item descriptions, not only the README)
- [ ] **Gate 2: Sophia has reviewed the code and can modify it unaided** (see above)
- [ ] `python tools/build-release.py --check-only` passes
- [ ] `drip check` is clean
- [ ] **The bundle store has been regenerated since the last change to `PROMOTIONS` or
      `RENAMES`** in `tools/convert-legacy.py`. Those tables decide which bundles belong in the
      store and under what name, so a store built before a change to them is stale. Regenerate
      it with the converter rather than patching by hand — it is downstream of the converter and
      can't be maintained independently of it:

      ```bash
      python tools/convert-legacy.py --part 1 --out <store path> --bundles copy
      ```

      This has already bitten once: `SLING_OLIVEDRAB_BAG` was promoted from Part 3, the store
      predated the promotion, and the item would have shipped with no model. The converter
      itself was already correct — a promoted item's co-located bundles travel with it — so the
      fix was to regenerate, not to copy a file across.
- [ ] Prices reviewed (`Review Prices.cmd`) — see `REVIEWING-PRICES.md`
- [ ] Any filename `DRIP-113` flags is renamed. **Renaming is free before release and permanent
      after** — the filename derives the item id, and once a player has the item in a stash it
      can't change.
- [ ] `<Version>` in `DRIP.csproj` bumped — it stamps both the archive names and each add-on's
      `pack-info.json`
- [ ] **The bundle-store assets are uploaded to the release** (`--store-only` if nothing else
      changed). They are what Setup.cmd installs on a fresh clone; a release without them is
      a release new developers can't bootstrap from.
- [ ] Add-on packs rebuilt against the same version, if any are shipping alongside the base

## `dist/` is build output

It holds a full staged copy plus the zip, so several gigabytes. It should be git-ignored and is
safe to delete at any time.
